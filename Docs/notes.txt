(Q) Why there are two tables Job & Job_runs?

The `Job` table stores the definition of the work that needs to be performed. It contains the job's configuration, such as its schedule, execution type, retry policy, and other metadata. Each job is created only once.

The `Job_Runs` table stores the **actual execution instances** of a job. Every time a job is triggered—whether by its schedule, a manual execution, or a retry—a new record is created in `Job_Runs`. This allows a single job to have multiple execution instances, each with its own status, timestamps, logs, retry count, and execution result.

Separating these tables provides a clear distinction between the **job definition** and its **execution history**, making it easier to track past runs, monitor failures, handle retries, and maintain a complete audit trail.

 If the job gets failed to execute then the executor will push the job back in to the kafka queue, but the executor service unlike watcher service will not push the job in the 'run' topic, but in the separate topic as 'retry', Now when the Job_consumer_svc picks this job from the kafka queue, the Job_consumer_svc will need to inform the Job_table also that this is 2nd, 3rd or nth attempt to execute this job, so Job_Consumer_Svc will increment attempt_number field of job entity by +1 respectively, and push it in the Job_table (via Kafka(ingest) -> Consumer_Svc -> Job_table) 

This above flow will be helpful to retry a job that did not got executed in the previous attempt, but if a job still not finshied even after perticluar attempt numbers like (10 attempts), then to avoid this infinite looping issue, we have a solution for this,that is before the executor push the failed job back in the kafka queue it will compare the attempt number with the 'retires'(allowed retries by user) filed of the Job entity if it execceds then push it the 'dead' topic instead of the retry topic, then watcher will push it in the 'dead' topic of the kafka queue,

=> found out one issue in the system, when the job_svc push the job CRUD messages in the kafka(ingest) then the consumer-svc fetches from the kafka broker, to mantain the consistency we will be having all the CUD operations in the same kafka topic as "job-commands" but the issue is when the consumer-svc fetches the job-commands from the kafka broker, it will be having multiple instances of consumer-svc running in parallel, so if we have a case where one instance of consumer-svc is fetching a job-commands message to update the job entity in the Job_table and at the same time another instance of consumer-svc is fetching a job-commands message to delete the same job entity in the Job_table then this will create a race condition and will lead to inconsistency in the Job_table, or a job is not created yet and the consumer-svc instance is trying to update it, so to avoid this we will be pushing the messages of the same job entity in the same partition of the kafka topic, so that all the messages of a particular job entity will be fetched by the same instance of consumer-svc and this will avoid the race condition and inconsistency in the Job_table. For this our kafka producer (job_svc) will be having the partition key as the job_id of the job entity, so that all the messages of a particular job entity will be pushed in the same partition of the kafka topic.
But the issue is while creating the job, since the job_id is generated by the Job_table, so we will not have the job_id while creating the job, so to avoid this we will be having a unique key for each job entity which will be generated by the job_svc and this unique key will be used as the partition key for the kafka topic, so that all the messages of a particular job entity will be pushed in the same partition of the kafka topic.
We will be using ULID (Universally Unique Lexicographically Sortable Identifier) as the unique key for each job entity, which will be generated by the job_svc and this unique key will be used as the partition key for the kafka topic, so that all the messages of a particular job entity will be pushed in the same partition of the kafka topic.

Question arised in my mind: will it slow down the search by id operation for the job_search_svc since the id will ULID instead of table genrated sequnced ids like 1,2,3,... 

Answer = No — point lookups by ID aren't meaningfully slower with ULID/UUID vs an integer.

Why: A B-tree index gives O(log n) lookup regardless of whether the key is sequential or random. When the client searches `WHERE job_id = 'xyz'`, Postgres walks the index the same way whether the key is `42` or a ULID — key randomness only hurts *insert* locality (where new rows land in the tree), not *lookup* cost. Once the index exists, an exact-match query against it is equally fast either way.

What actually changes, and it's minor:
- Index/storage size — UUID/ULID is 16 bytes vs 4 bytes (int) or 8 bytes (bigint). A larger key means a slightly wider B-tree, so marginally more pages to traverse/cache at very large scale — but this is a rounding-error difference for point lookups, not something you'd notice until you're at hundreds of millions of rows.
- Range queries / sorting by ID — this is where it matters more. `ORDER BY job_id` or `WHERE job_id BETWEEN x AND y` is meaningless with random UUIDv4 but works naturally with ULID/UUIDv7 since they're time-ordered — another point in favor of picking the ordered variant.
- **String comparison cost** — if you store ULID as text rather than as a native 128-bit type, string comparisons are somewhat costlier than integer comparisons. Store it as `UUID` type in Postgres (or `BYTEA`/native binary if using raw ULID) rather than `VARCHAR`, and this is a non-issue.

So the practical guidance: use `UUID` as the Postgres column type (not text), generate UUIDv7/ULID client-side, and your `job_search_service` read path won't see any meaningful slowdown on ID lookups. The real performance lever for your search service will be whatever secondary indexes you put on filterable fields (status, job type, created_at) — not the primary key choice.

In the consumer-svc, what if the the situation occur as :- what if the consumer service consumed a job cmd, persisted it to the DB and before ack it to the kakfa to update the kafka offset, something goes down, and when restarted, as the offset is still on the same kafka message the job cmd gets executed twice or job get persisted twice.

=> To avoid this situation i was going to use hashing approch in which just hash the content of the job cmd and store it in the DB, and before persisting the job cmd to the DB, check if the hash of the job cmd already exists in the DB, if yes then do not persist it again, but this will not work because suppose a cmd is to update the staus from active to paused and again active cmd comes, then both the active cmds will have the same hash and the second cmd will not be persisted, so this approach will not work.

Instead we will use the eventID based approch in which each job cmd will have a unique eventID generated by the job_svc and this eventID will be stored in the DB along with the job cmd, and before persisting the job cmd to the DB, check if the eventID of the job cmd already exists in the DB, if yes then do not persist it again, this will ensure that even if the same job cmd is consumed twice by the consumer-svc, it will not be persisted twice in the DB.


What if the service crashes?

Case 1 — crashes before DB commit
BEGIN TRANSACTION
       │
       ├── update Job
       │
       ├── save eventId
       │
       💥 CRASH

Because the transaction wasn't committed:

Job change → ROLLBACK
eventId    → ROLLBACK

Nothing is persisted.

Kafka offset also wasn't committed, so after restart:

Kafka redelivers message
        ↓
eventId doesn't exist
        ↓
process Job
        ↓
save eventId
        ↓
COMMIT
        ↓
Kafka offset commit

Perfect.


Case 2 — DB commits, then service crashes
BEGIN TRANSACTION
       │
       ├── update Job ✓
       ├── save eventId ✓
       │
       ▼
    COMMIT ✓
       │
       💥 CRASH
       │
       ▼
Kafka offset NOT committed

After restart:

Kafka redelivers message
        ↓
eventId exists
        ↓
ignore
        ↓
Kafka offset commit

Again, perfect.

Major modifaction took place in the system,

for implementing the distributed watcher service, we have added two new fields in the Job entity as 'next_run_time' and 'last_polled_time', and also added a composite index on these two fields along with the status field, to make the watcher service to query the jobs faster.

why this two fields are needed, because the watcher service will be running in multiple instances and each instance will be polling the jobs from the Job_table, so to avoid the duplicate polling of the same job by multiple instances of watcher service, we need to have these two fields, so that each instance of watcher service can poll the jobs based on these two fields and also update the last_polled_time field after polling the jobs, so that other instances of watcher service will not poll the same jobs again.

the watcher service will be polling the jobs based on the next_run_time field, which is the time when the job is scheduled to run next, and the last_polled_time field, which is the time when the job was last polled by any instance of watcher service.

 SELECT * FROM jobs WHERE status IN ('scheduled', 'running') AND next_run_time <= NOW() AND last_polled_time < (NOW - 30s) LIMIT 1000

why the NOW() - 30s is used in the above query, because we want to avoid the duplicate polling of the same job by multiple instances of watcher service, so we are adding a buffer time of 30 seconds, so that if any instance of watcher service is polling the jobs and it sees that the last_pool_time is more than 30 secs that means the instance of watcher service which polled this job is facing some issue and is not able to process the job in time, so other instances of watcher service can poll this job again and process it, but if the last_polled_time is less than 30 secs that means the instance of watcher service which polled this job is still processing it and other instances of watcher service should not poll this job again to avoid duplicate processing of the same job.

what if the 30s passes ?
this situation may occur if the watcher service is down or facing some issue and it is not able to process the jobs in time, so to avoid this situation we are adding a buffer time of 30 seconds, so that if any instance of watcher service is polling the jobs and it takes more than 30 seconds to process the jobs, then other instances of watcher service will not poll the same jobs again.
=> If the 30s passes and the job is still not processed by any instance of watcher service, then the job will be polled again by other instances of watcher service, but this time the last_polled_time field will be updated to the current time, so that other instances of watcher service will not poll the same jobs again.

Also the job status has been updated to add two new status as 'COMPLETED' and 'FAILED_PERMANENTLY', the 'COMPLETED' status is used when the job is completed successfully and the 'FAILED_PERMANENTLY' status is used when the job has failed after all the retries and it will be moved to the dead letter queue.

Also while publishg to the kafka run topic the watcher service will be passing the run_id ULID field as well this will ensure idepotency

If Watcher generates run_id:
=> If Kafka re-delivers the message (due to a consumer restart, timeout, or partition rebalance), the consumer sees the same run_id. It can check jobRunRepository.existsById(runId) or rely on a DB unique constraint to say: "I already created this run record, ignore duplicate."

If Consumer generates run_id:
=> Every time the consumer picks up the message, it generates a new run_id and inserts a duplicate row into job_runs. You end up running the same scheduled job multiple times.

as we choose to have the run_id generated by the watcher service, so that the consumer can check if the run_id already exists in the job_runs table, if it exists then it will not create a new job_run entry and will ignore the duplicate message from kafka.
