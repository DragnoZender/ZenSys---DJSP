(Q) Why there are two tables Job & Job_runs?

The `Job` table stores the definition of the work that needs to be performed. It contains the job's configuration, such as its schedule, execution type, retry policy, and other metadata. Each job is created only once.

The `Job_Runs` table stores the **actual execution instances** of a job. Every time a job is triggered—whether by its schedule, a manual execution, or a retry—a new record is created in `Job_Runs`. This allows a single job to have multiple execution instances, each with its own status, timestamps, logs, retry count, and execution result.

Separating these tables provides a clear distinction between the **job definition** and its **execution history**, making it easier to track past runs, monitor failures, handle retries, and maintain a complete audit trail.

Question arised in my mind: will it slow down the search by id operation for the job_search_svc since the id will ULID instead of table genrated sequnced ids like 1,2,3,... 

Answer = No — point lookups by ID aren't meaningfully slower with ULID/UUID vs an integer.

Why: A B-tree index gives O(log n) lookup regardless of whether the key is sequential or random. When the client searches `WHERE job_id = 'xyz'`, Postgres walks the index the same way whether the key is `42` or a ULID — key randomness only hurts *insert* locality (where new rows land in the tree), not *lookup* cost. Once the index exists, an exact-match query against it is equally fast either way.

What actually changes, and it's minor:
- Index/storage size — UUID/ULID is 16 bytes vs 4 bytes (int) or 8 bytes (bigint). A larger key means a slightly wider B-tree, so marginally more pages to traverse/cache at very large scale — but this is a rounding-error difference for point lookups, not something you'd notice until you're at hundreds of millions of rows.
- Range queries / sorting by ID — this is where it matters more. `ORDER BY job_id` or `WHERE job_id BETWEEN x AND y` is meaningless with random UUIDv4 but works naturally with ULID/UUIDv7 since they're time-ordered — another point in favor of picking the ordered variant.
- **String comparison cost** — if you store ULID as text rather than as a native 128-bit type, string comparisons are somewhat costlier than integer comparisons. Store it as `UUID` type in Postgres (or `BYTEA`/native binary if using raw ULID) rather than `VARCHAR`, and this is a non-issue.

So the practical guidance: use `UUID` as the Postgres column type (not text), generate UUIDv7/ULID client-side, and your `job_search_service` read path won't see any meaningful slowdown on ID lookups. The real performance lever for your search service will be whatever secondary indexes you put on filterable fields (status, job type, created_at) — not the primary key choice.

The Problem Layer 2 Solves: "Out-of-Order or Delayed Messages"
Imagine a job that runs very fast (e.g., in 100 milliseconds).

Here is what happens in the executor:

At 0ms: The executor starts the job ->  sends event: status = RUNNING
At 100ms: The executor finishes the job -> sends event: status = SUCCESS

Now imagine there is a small network hiccup or delay:

The SUCCESS message arrives at consumer-service first.
consumer-service updates PostgreSQL: status = SUCCESS.
A moment later, the delayed RUNNING message finally arrives

The database status would change from SUCCESS back to RUNNING! Your dashboard would show a completed job as still running forever. this is the problem of out-of-order or delayed messages, which is a common issue in distributed systems.

In any job execution system, status can only move forward, never backward:

┌─────────┐      ┌─────────┐      ┌─────────┐
│ PENDING │ ───▶ │ RUNNING │ ───▶ │ SUCCESS │
└─────────┘      └─────────┘      └─────────┘
                       │
                       └──────────▶ ┌────────┐
                                    │ FAILED │
                                    └────────┘

Once a job reaches a finished state (SUCCESS or FAILED), nothing is ever allowed to change it back.

so in our solution, When consumer-service receives an event for a runId, it looks at the current status already saved in PostgreSQL before updating:

// Rule 1: If it's already finished, IGNORE any incoming message
if (currentRun.getStatus() == JobRunStatus.SUCCESS || currentRun.getStatus() == JobRunStatus.FAILED) {
    log.info("Run {} is already finished ({}). Ignoring event {}", 
             currentRun.getId(), currentRun.getStatus(), event.getStatus());
    return; // Do nothing!
}

// Rule 2: Only transition PENDING -> RUNNING
if (event.getStatus() == JobRunStatus.RUNNING) {
    if (currentRun.getStatus() == JobRunStatus.PENDING) {
        currentRun.setStatus(JobRunStatus.RUNNING);
        currentRun.setStartTime(event.getTimestamp());
    }
}

// Rule 3: Transition RUNNING (or PENDING) -> SUCCESS / FAILED
if (event.getStatus() == JobRunStatus.SUCCESS) {
    currentRun.setStatus(JobRunStatus.SUCCESS);
    currentRun.setEndTime(event.getTimestamp());
}
jobRunRepository.save(currentRun);

Layer 1 (eventId): Checks "Have I already seen this exact message before?" (prevents duplicate processing).
Layer 2 (State check): Checks "Does it make business sense to update the database from the current status to the new status?" (prevents old or out-of-order messages from corrupting the state)

Together, they make your system 100% resilient to network lag, retries, and duplicate messages!

PostgreSQL does not update rows in place. Every UPDATE writes a new row version to disk and leaves dead tuples behind. 500 writes/sec just to update a timestamp column will:
1. Cause massive table bloat on job_runs.
2. Put heavy lock contention and write IOPS on the database.
3. Force PostgreSQL autovacuum to run aggressively, eating up CPU.

Hence to avoid this issue, while still keeping the executor-service heartbeat checking functionality we will use the Redis cache

How the Redis Heartbeat Approach Actually Works
This pattern is known in engineering as a "Dead Man's Switch" (like in trains, where the driver must press a pedal every 30 seconds; if the driver passes out and stops pressing, the train automatically detects it).

Step 2: While Healthy
        - Every 10 seconds, the executor refreshes the key.
        - The 30-second countdown resets back to 30.
        - As long as the executor is healthy, the key never dies.

Step 3: What Happens if the Executor Crashes?
        - The worker process dies (power cut, machine failure, killed by OS).
        - It stops sending heartbeats.
        - After 30 seconds, Redis automatically evicts the key from memory.

Step 4: Watcher Recovers the Abandoned Jobs
        - watcher-service periodically scans running jobs:

        It queries: SELECT * FROM job_runs WHERE status = 'RUNNING'
        For each running job, it checks: redisTemplate.hasKey("executor:" + run.getExecutorId() + ":heartbeat")

        If the key exists: 
                - the worker is alive, job is fine.

        If the key is gone:
                - The worker has died!
                - Watcher marks that run as status = 'EXECUTOR_DIED' in the database.
                - Watcher re-publishes the job to Kafka run topic so another healthy worker can pick it up.

3. High Scale: 10,000 executors sending heartbeats every 10 seconds to Redis consumes less than 2% of Redis's CPU capacity.

The Problem with a Single Thread: "Head-of-Line Blocking"

Imagine you are running a single thread, and two jobs arrive at your executor:

Job 1: An HTTP webhook that takes 10 seconds to respond.
Job 2: A quick task that takes 100 milliseconds.

If you only have 1 thread:

The single thread is 100% occupied running Job 1 for the next 10 seconds.

Job 2 arrives at 0.1s, but cannot start. It is forced to wait in a queue for 9.9 seconds until Job 1 completely finishes!


If 10 jobs arrive at once, and each takes 10 seconds:
Job 1 finishes at 10s
Job 2 finishes at 20s
Job 10 finishes at 100s!

Your server's CPU and RAM are 95% idle, but your system is creeping at a snail's pace because jobs are running sequentially in a single file line.


Why a Thread Pool (e.g. 20 Threads)?
Most jobs are I/O bound (waiting for an HTTP API to respond, waiting for a database query, or sleeping):

While Thread 1 is sitting idle waiting for an external HTTP server to reply, the CPU is doing nothing.
With a pool of 20 threads, 20 jobs can run at the exact same time in parallel:
20 jobs that each take 10 seconds will all finish in 10 seconds (instead of taking 200 seconds!).

Why MAANG Architects Insist on Republishing to run:
1. Single Source of Truth (run topic): The dispatcher service has only one job: take work that is ready right now and dispatch it to an executor. It does not care whether the job is brand new from watcher-service, a retry from attempt 2, or an ad-hoc trigger from a user!
2. Independent Scaling: The component managing retries scales independently from the workers executing jobs.
3. Strict Durability: A job waiting for a retry is stored in a durable delay mechanism (e.g. Redis Sorted Set with timestamps or tiered Kafka delay topics). If the service crashes, the timer is not lost. When the timer hits zero, it is emitted to run.

How to Answer This in an Interview (Verbatim Script)

"In Kafka, we avoid in-memory sleep or delaying directly inside the dispatcher consumer because Kafka is not a point-to-point delay queue—sleeping causes partition head-of-line blocking and risking message loss on pod termination.
Instead, we follow the Canonical Ingress Funnel pattern: failed tasks with remaining retries are placed into a delayed retry pipeline with exponential backoff. Once the delay elapsed, the message is re-published to the primary run topic with an incremented attempt count.
This decouples execution dispatching from scheduling delays, ensures the run topic remains the single source of truth, and guarantees at-least-once execution even if nodes crash during the backoff period."

The MAANG-Grade Solution: Visibility Timeout (Leasing Pattern) :

This is the exact pattern used by AWS SQS, Temporal, Cadence, and Celery:

Rule: Never delete an item from the queue until the downstream destination (Kafka) confirms with a broker acknowledgment (ACK).

Instead of deleting (ZREM) the item upfront, the sweeper claims a temporary lease on the item by bumping its score into the future (e.g., $+30$ seconds):

This removes the {selection + deletion} atomic flow and instead implments {Selecting + Leasing (Hiding)} is 100% atomic.

what is Leasing? 
- Suppose current time is 12:00:00 (timestamp: 1000). The sweeper finds an item with score 1000.
Instead of deleting it, it bumps its score into the future by $+30$ seconds: {New Score} = 1000 + 30000 = 31000 (12:00:30)
Now, that item is still in Redis, but it is hidden (leased) because its score is in the future. No other sweeper instance will touch it

And during this 30 secs gap it is expected that the spring kafka will publish this data in the kafka 'run' topic

Outcome A: The Normal Case (Success)
        1. Sweeper gets the item.
        2. Sweeper publishes it to Kafka and waits for Kafka's broker ACK.
        3. Kafka says: "Got it, safely saved to disk!"
        4. Sweeper deletes the item from Redis:
                redisTemplate.opsForZSet().remove(zsetKey, itemJson);
                The lease is closed, and the task is done.


Outcome B: The Crash Case (Zero Data Loss!)
        1. Sweeper gets the item (score was pushed to 12:00:30). as {section + leasing} is atomic
        2. The machine suddenly crashes / loses power before sending to Kafka.
        3. At 12:00:30 (30 seconds later):
                1. The current time becomes 12:00:30.
                2. The item's score is now <= currentTime again!
                3. Another running instance of retry-service (or the restarted pod) sees the item is due again and picks it up!
                4. No message is ever lost.

** Why is Leasing So Popular in Big Tech (AWS, Netflix, Uber)?
        -Amazon SQS calls this Visibility Timeout.
        -Google Chubby & Apache ZooKeeper use leases to detect dead master nodes.
        -Why? Because in distributed systems, network partitions and hardware crashes are guaranteed to happen. A lease ensures you don't need complicated monitoring to recover lost tasks — time itself cleans up and recovers the task automatically.

The Solution: Atomic Ingestion via Lua Script :- 

=> In distributed systems, whenever you need to deduplicate AND queue an item, doing them as two separate network calls (SETNX then ZADD) will always leave a vulnerability window between the two commands.
The MAANG standard is to execute both operations atomically inside a single Redis Lua script:

```

local zset_key = KEYS[2]

local dedup_ttl = tonumber(ARGV[1])
local due_timestamp = tonumber(ARGV[2])
local item_json = ARGV[3]

-- 1. Try to set the deduplication key atomically (SETNX with EX)
local set_result = redis.call('SET', dedup_key, '1', 'EX', dedup_ttl, 'NX')

if not set_result then
    -- Key already exists -> True duplicate redelivery from Kafka
    return 0
end

-- 2. New message -> Atomically add to delayed queue in the same transaction!
redis.call('ZADD', zset_key, due_timestamp, item_json)
return 1

```


Why This Completely Eliminates the Bug ?
=> Because Redis executes Lua scripts atomically on a single thread:

It is physically impossible for a crash to occur between the SET and the ZADD.

Case 1: Crash before the Lua script runs: Neither the dedup key nor the ZSET item is in Redis. When Kafka redelivers, it is treated as new and processed normally.

Case 2: Crash after the Lua script runs (before Kafka commits offset): Both the dedup key and the ZSET item already exist in Redis. When Kafka redelivers, the Lua script returns 0 (duplicate) and skips it. The item is already safely in retry:delayed waiting to be swept and executed!
Bonus performance win: It cuts network latency in half (1 round-trip to Redis instead of 2).

so this ensure that both key and item stored or none.



Q. Does current implementation gurantee that the kafka offset is only committed when Deduplication and adding corresponding DelayedRetryItem is stored in the redis ?

Yes, the current implementation guarantees that the Kafka offset is only committed after the deduplication and delayed item are stored in Redis.

Here is the exact technical breakdown of why:

There are 3 foundational mechanisms in Spring Boot + Spring Kafka at work:

A. Spring Boot Disables Kafka Auto-Commit by Default :
In raw Kafka, if enable.auto.commit = true, a background thread commits offsets every 5 seconds regardless of your code. In Spring Kafka, enable.auto.commit is set to false by default. Kafka never commits offsets on a timer in the background.


B. Synchronous & Blocking Execution

In RetryEventConsumer.java :

```
@KafkaListener(...)
public void consume(JobRetryEvent event) {
    ...
    // 1. Synchronous blocking call to Redis
    Long result = redisTemplate.execute(...);

    // 2. Only if Redis succeeds does this method return normally
}

```

redisTemplate.execute(...) is a blocking network call. The listener thread cannot exit consume() until Redis has completely finished the Lua transaction and returned the result to the JVM.

also, because RetryEventConsumer.consume() is a synchronous Java method, it is impossible for Spring Kafka to acknowledge/commit the message before RetryEventConsumer.consume() has completely finished storing the item in Redis.




C. Exception Aborts Offset Commit
If Redis is down, times out, or throws any error:

```

catch (Exception e) {
    throw new RuntimeException("Redis atomic buffering failed for retry item", e);
}

```

When an unhandled exception bubbles out of @KafkaListener:
        - Spring Kafka’s ListenerConsumer catches the exception.
        - It explicitly refrains from committing the offset of that record.
        - The record will remain uncommitted and will be re-polled / retried according to the error handler.





*** The Nuance: Default AckMode.BATCH vs AckMode.RECORD ***

By default, Spring Kafka uses AckMode.BATCH:

If Kafka polls 5 retry messages in one poll:
        - Message 1: Stored in Redis.
        - Message 2: Stored in Redis.
        - Pod crashes on Message 3.

Because the entire batch didn't finish, offsets for Messages 1 & 2 might not have been flushed to Kafka yet.

When the service restarts, Kafka redelivers Message 1.

Is this a problem? 
=> No! Because our Atomic Lua Ingestion script sees the key in Redis, returns 0 (duplicate), logs a warning, and safely skips it without adding it to the queue twice.

The Two Architectural Philosophies in Distributed Schedulers

Philosophy A: Circuit Breaker / Fail-Safe Stop (Current Codebase)

How it works: If all retries for an occurrence fail, the parent schedule is stopped permanently (FAILED_PERMANENTLY).

Why systems use this:
        - If a job fails because an external database is unreachable, credentials expired, or bad code was deployed, continuing to run every minute/hour will just flood Kafka with dead letters, hammer failing downstream systems, and waste compute.
        - It acts as an automated Circuit Breaker: halt execution, alert the on-call engineer, and wait for manual fix + resume.


Philosophy B: Resilient Recurring Schedule (Per-Occurrence Failure)

How it works:
        - The specific execution attempt is marked permanently failed in job_runs (JobRun.status = FAILED), and an alert is sent to the Dead Letter Queue.
        - However, the parent Job is reset to SCHEDULED so tomorrow’s run (or the next interval) is still attempted.
        - Only ScheduleType.ONCE jobs transition to FAILED_PERMANENTLY.

Why systems use this (e.g., Kubernetes CronJob, Linux cron):
        - The failure might be transient to that specific run's window (e.g., network blip or temporary 10-minute downstream outage).
        - Permanently disabling the entire schedule can silently drop future runs unless someone actively monitors alerts.



Since I building and scaling ZenSys to handle complex, enterprise workflows like Apache Airflow, Temporal, or Kubernetes, Philosophy B (Per-Occurrence Failure / Resilient Recurring Schedule) is overwhelmingly the best-suited architecture.

Here is why:

1. The Core Principle: Definition vs. Instance Separation

In systems like Apache Airflow, Temporal, and Kubernetes:
        - The Definition (Job / DAG) represents the standing contract or intent (e.g., "Run this pipeline every day at midnight").
        - The Execution (JobRun / DagRun) represents a single instance in time (e.g., "Execution for Monday, Sept 16").

A single JobRun failing an execution should never corrupt or kill the standing schedule contract.
        - In Apache Airflow, if Monday’s DagRun fails all retries, Monday’s status becomes FAILED, but the DAG remains active (SCHEDULED). Tuesday’s run will trigger automatically.
        - In Kubernetes CronJob, if a pod crashes and exhausts retries, that Job instance is marked FAILED, but the CronJob controller does not delete or stop future cron schedules.


2. Resilience Against Transient External Failures

In real-world distributed architectures:
        - 90% of job failures are transient (e.g., an upstream microservice had a 15-minute outage, a third-party API returned 503, a database lock timed out, or daily batch files arrived 20 minutes late).
        - If Monday’s 2 AM failure sets the Job to FAILED_PERMANENTLY:
                - Tuesday, Wednesday, and Thursday will silently never run.
                - On-call engineers would have to manually log in, inspect DBs, and un-pause/resurrect every single cron job after transient network blips.

        With Philosophy B:
                - Monday's run is recorded as FAILED in job_runs and dispatched to the DLQ (dead topic) for alerting (PagerDuty/Slack).
                - The parent Job returns to SCHEDULED, and Tuesday's run attempts normally.

Step 1: The Setup (The Two Tables & Two Threads)
In ZenSys, we have:
        - jobs table (The parent job definition: e.g., Job "Daily-ETL", schedule CRON).
        - job_runs table (A single execution instance: e.g., Run run-001, status PENDING, RUNNING, or FAILED).

And inside consumer-service, we have two separate Kafka threads:
        - Thread A (job-run-events topic): Receives RUNNING, SUCCESS, FAILED packets.
        - Thread B (dead topic): Receives JobDeadEvent when all 3 retries are exhausted.


Step 2: How the Race Condition Happens

Suppose a CRON job reaches attempt 3 and fails:        
        - The executor sends a RUNNING event to Kafka topic job-run-events (for Thread A).
        - The executor then sends a JobDeadEvent to Kafka topic dead (for Thread B).

Because Kafka topics are completely independent, Thread B can process the JobDeadEvent faster than Thread A processes the RUNNING event!

--------------------------------------------------
|Time 1: Thread B receives JobDeadEvent          | 
|Time 2: Thread A receives delayed RUNNING event |
--------------------------------------------------


Step 3: Where the Problem Appears in "Philosophy B"

Now look at what happens at Time 1 and Time 2:
        
        At Time 1 (Thread B runs processDeadEvent):
                - In Philosophy B, for a CRON job, we want tomorrow’s run to still happen, so Thread B says:
                        => "Attempt 3 died, but this is a CRON job, so I must keep the job ready for tomorrow!" -> job.setStatus(JobStatus.SCHEDULED)

                At this exact moment:
                - The Job status in the DB is SCHEDULED.
                - But Thread A hasn't written anything to job_runs yet, so job_runs table has NO ROW for run-001!

        At Time 2 (Thread A finally receives the delayed RUNNING event for run-001):
                - Thread A wakes up and looks at the database:
                        => Does run-001 exist in job_runs table? No! It's empty.
                - Thread A thinks: "Aha! This is a brand-new run that just started!"

                - Thread A checks if the parent Job is in a terminal state (isJobInTerminalState):
                        => Is SCHEDULED a terminal state? NO! SCHEDULED means the job is alive!

                - So Thread A executes this line
                
                ```
                job.setStatus(JobStatus.RUNNING); // <--- DISASTER!
                jobRepository.save(job);

                ```

The Disaster:
- The job was supposed to stay SCHEDULED for tomorrow.
- But Thread A's delayed packet overwrites it back to RUNNING!
- And because all retries already died on Thread B, no more events are ever coming for this run!
- The CRON job is now permanently frozen in RUNNING forever, and tomorrow’s run will never trigger!



Step 4: Why Did This Happen?
=> Because Thread B only updated the jobs table, but forgot to create the record in job_runs!
and since because job_runs was empty, Thread A was tricked into thinking: "This is a new run that just started."


Step 5: The Solution (How We Fix It Completely)

=> The fix is one simple rule: When Thread B processes JobDeadEvent, it must immediately write run-001 into job_runs as FAILED.

In code:

```

run.setErrorMsg(event.getErrorMsg());

```

                ```

Step-by-Step Execution Flow

Here is the exact lifecycle of a message arriving at JobConsumer.java:


Kafka Broker
     │
     ▼ (1) poll() fetches message
Spring Kafka Listener Container
     │
     ▼ (2) Invokes listener method
JobConsumer.consume(command)
     │
     ▼ (3) Calls business & DB logic
JobPersistenceService.processJobCommand(command)
     │   ├── Checks processed_commands for eventId
     │   ├── Persists job in PostgreSQL (@Transactional)
     │   └── Saves eventId in processed_commands
     │
     ▼ (4) Method completes successfully
Spring Kafka Listener Container
     │
     ▼ (5) Commits offset to Kafka broker (__consumer_offsets)
Kafka Broker




Key Scenarios

Scenario 1: Normal Successful Execution

        1. consume(command) is called.
        2. processJobCommand(command) finishes writing to PostgreSQL and commits the database transaction.
        3. Control returns cleanly to Spring Kafka's listener container.
        3. Spring Kafka commits the offset to Kafka. The broker now knows this message has been successfully processed.

Scenario 2: Exception Thrown During processJobCommand()
        1. If PostgreSQL is down, or a DB constraint fails, an exception is thrown out of processJobCommand().
        2. The database transaction rolls back.
        3. Spring Kafka intercepts the exception.
        4. The offset is NOT committed to Kafka.
        5. Depending on error handling / retry configuration, Spring Kafka will retry the message or redeliver it on the next poll cycle.


Scenario 3: Service Crashes Mid-Execution
        1. The service is in the middle of executing processJobCommand(), or crashes immediately after writing to the database before the network call to commit the offset to Kafka completes.
        2. Because the offset was never committed to Kafka, when the service restarts, Kafka will redeliver the exact same message (At-Least-Once Delivery).
        3. When the redelivered message reaches processJobCommand():
        ```
        if (processedCommandRepository.existsById(command.getEventId())) {
                return; // Ensuring Idempotency
        }

        ```
        The idempotency check in JobPersistenceService.java detects that eventId was already processed, skips duplicate execution, and control returns cleanly so Spring Kafka can now successfully commit the offset!

How Spring Kafka Controls This :- 
Under the hood in KafkaConsumerConfig.java: => 
- By default, Spring Kafka disables raw Kafka's client-side periodic auto-commit (enable.auto.commit = false).
- Instead, Spring's ConcurrentKafkaListenerContainerFactory manages offset commits using its ContainerProperties.AckMode (default is AckMode.BATCH).
- In this mode, the container only commits the offset to the broker after the listener method has returned without throwing an unhandled exception.

        ```

        And in JobWatcherService.java:

        ```
        // 1. Publish execution command to Kafka 'run' topic (fire-and-forget)
        runProducer.sendRunEvent(runEvent);

        // 2. Advance job schedule and status based on schedule type
        advanceJobSchedule(job, now);

        // 3. Mark last polled timestamp and persist changes
        job.setLastPolledTime(now);
        jobRepository.save(job);

        ```


        The Problem:

        - kafkaTemplate.send(...) is non-blocking and asynchronous. It immediately returns without waiting for Kafka broker ACK.

        - If Kafka is temporarily unreachable, the buffer is full, or partition metadata is missing:
                - sendRunEvent will not throw an exception synchronously.
                - The code immediately proceeds to advanceJobSchedule() and saves the job to Postgres!
                - For a ONCE job: nextRunTime is set to null.
                - For a CRON job: nextRunTime is advanced to tomorrow.

        - Result (Silent Data Loss): The database thinks the job was triggered and advanced, but the Kafka message was dropped in the background. The job execution is permanently lost.



Vulnerability 3: The Classic Dual-Write Problem (Kafka vs. Database)  (issue to atmost or exactly once behaviour)

        The Problem: What happens if the service crashes, JVM terminates, or database connection drops right on line 81 (jobRepository.save(job)), after Kafka send?

                - The Kafka message is already published to the run topic.
                - executor-service consumes it and starts executing the job.
                - But the DB transaction rolls back (or was never saved).
                - On the next watcher poll (20s later), the database still has nextRunTime <= NOW().
                - Watcher pulls the exact same job again and publishes a second run!


        Result: Phantom duplicate runs.


Vulnerability 4: Large @Transactional Scope on Batch Loop

                - In the next cycle, jobs #1 to -#500 will all be re-polled and re-dispatched.

How MAANG-Grade Systems Fix This

        To make this flow completely rock-solid and enterprise-grade:
        
        1. PostgreSQL Row-Locking (FOR UPDATE SKIP LOCKED): Change findDueJobs query to lock rows atomically:
        
                SQL
                ```
                SELECT j FROM Job j
                WHERE j.status IN ('SCHEDULED', 'RUNNING')
                  AND j.nextRunTime <= :now
                  AND (j.lastPolledTime IS NULL OR j.lastPolledTime < :threshold)
                ORDER BY j.nextRunTime ASC
                FOR UPDATE SKIP LOCKED
        
                ```
                Any other watcher instance will automatically skip already-locked jobs without blocking!
        
        2. Synchronous Kafka ACK (SendResult.get(5, TimeUnit.SECONDS)): Just like we did in retry-service, synchronously wait for Kafka broker ACK before advancing the database schedule. If Kafka fails, fail fast and do not advance the DB.

1. How the Changes Fix Vulnerability 1 (Multi-Watcher Concurrency)

        The Change:
        In JobRepository.java: Add pessimistic locking with PostgreSQL SKIP LOCKED:

        ```
        @Lock(LockModeType.PESSIMISTIC_WRITE)
        @QueryHints({@QueryHint(name = "jakarta.persistence.lock.timeout", value = "-2")}) // -2 tells Postgres: SKIP LOCKED
        @Query("""
                SELECT j FROM Job j
                WHERE j.status IN ('SCHEDULED', 'RUNNING')
                  AND j.nextRunTime <= :now
                  AND (j.lastPolledTime IS NULL OR j.lastPolledTime < :threshold)
                ORDER BY j.nextRunTime ASC
            """)
        List<Job> findDueJobs(
            @Param("now") Instant now,
            @Param("threshold") Instant threshold,
            Pageable pageable);

        ```

        Why it fixes the issue:
        - In PostgreSQL, FOR UPDATE SKIP LOCKED atomically places an exclusive row-level lock on the retrieved rows.
        - If Watcher Node 1 and Watcher Node 2 poll at the exact same millisecond:
                - Node 1 locks rows [1, 2, 3].
                - Node 2 does not block or read those rows; Postgres automatically skips rows [1, 2, 3] and gives Node 2 rows [4, 5, 6] (or empty list if no more jobs are due).

        - Verdict: 100% eliminates multi-watcher race conditions. No duplicate runs will be dispatched across multiple nodes.

        The Change:

        In distributed systems, updating two independent systems (PostgreSQL and Kafka) without distributed transactions (XA/2PC) has two failure modes:

        1. Catastrophic Failure Mode (Data Loss): DB commits -> Kafka send fails.
