(Q) Why there are two tables Job & Job_runs?

The `Job` table stores the definition of the work that needs to be performed. It contains the job's configuration, such as its schedule, execution type, retry policy, and other metadata. Each job is created only once.

The `Job_Runs` table stores the **actual execution instances** of a job. Every time a job is triggered—whether by its schedule, a manual execution, or a retry—a new record is created in `Job_Runs`. This allows a single job to have multiple execution instances, each with its own status, timestamps, logs, retry count, and execution result.

Separating these tables provides a clear distinction between the **job definition** and its **execution history**, making it easier to track past runs, monitor failures, handle retries, and maintain a complete audit trail.

Question arised in my mind: will it slow down the search by id operation for the job_search_svc since the id will ULID instead of table genrated sequnced ids like 1,2,3,... 

Answer = No — point lookups by ID aren't meaningfully slower with ULID/UUID vs an integer.

Why: A B-tree index gives O(log n) lookup regardless of whether the key is sequential or random. When the client searches `WHERE job_id = 'xyz'`, Postgres walks the index the same way whether the key is `42` or a ULID — key randomness only hurts *insert* locality (where new rows land in the tree), not *lookup* cost. Once the index exists, an exact-match query against it is equally fast either way.

What actually changes, and it's minor:
- Index/storage size — UUID/ULID is 16 bytes vs 4 bytes (int) or 8 bytes (bigint). A larger key means a slightly wider B-tree, so marginally more pages to traverse/cache at very large scale — but this is a rounding-error difference for point lookups, not something you'd notice until you're at hundreds of millions of rows.
- Range queries / sorting by ID — this is where it matters more. `ORDER BY job_id` or `WHERE job_id BETWEEN x AND y` is meaningless with random UUIDv4 but works naturally with ULID/UUIDv7 since they're time-ordered — another point in favor of picking the ordered variant.
- **String comparison cost** — if you store ULID as text rather than as a native 128-bit type, string comparisons are somewhat costlier than integer comparisons. Store it as `UUID` type in Postgres (or `BYTEA`/native binary if using raw ULID) rather than `VARCHAR`, and this is a non-issue.

So the practical guidance: use `UUID` as the Postgres column type (not text), generate UUIDv7/ULID client-side, and your `job_search_service` read path won't see any meaningful slowdown on ID lookups. The real performance lever for your search service will be whatever secondary indexes you put on filterable fields (status, job type, created_at) — not the primary key choice.

The Problem Layer 2 Solves: "Out-of-Order or Delayed Messages"
Imagine a job that runs very fast (e.g., in 100 milliseconds).

Here is what happens in the executor:

At 0ms: The executor starts the job ->  sends event: status = RUNNING
At 100ms: The executor finishes the job -> sends event: status = SUCCESS

Now imagine there is a small network hiccup or delay:

The SUCCESS message arrives at consumer-service first.
consumer-service updates PostgreSQL: status = SUCCESS.
A moment later, the delayed RUNNING message finally arrives

The database status would change from SUCCESS back to RUNNING! Your dashboard would show a completed job as still running forever. this is the problem of out-of-order or delayed messages, which is a common issue in distributed systems.

In any job execution system, status can only move forward, never backward:

┌─────────┐      ┌─────────┐      ┌─────────┐
│ PENDING │ ───▶ │ RUNNING │ ───▶ │ SUCCESS │
└─────────┘      └─────────┘      └─────────┘
                       │
                       └──────────▶ ┌────────┐
                                    │ FAILED │
                                    └────────┘

Once a job reaches a finished state (SUCCESS or FAILED), nothing is ever allowed to change it back.

so in our solution, When consumer-service receives an event for a runId, it looks at the current status already saved in PostgreSQL before updating:

// Rule 1: If it's already finished, IGNORE any incoming message
if (currentRun.getStatus() == JobRunStatus.SUCCESS || currentRun.getStatus() == JobRunStatus.FAILED) {
    log.info("Run {} is already finished ({}). Ignoring event {}", 
             currentRun.getId(), currentRun.getStatus(), event.getStatus());
    return; // Do nothing!
}

// Rule 2: Only transition PENDING -> RUNNING
if (event.getStatus() == JobRunStatus.RUNNING) {
    if (currentRun.getStatus() == JobRunStatus.PENDING) {
        currentRun.setStatus(JobRunStatus.RUNNING);
        currentRun.setStartTime(event.getTimestamp());
    }
}

// Rule 3: Transition RUNNING (or PENDING) -> SUCCESS / FAILED
if (event.getStatus() == JobRunStatus.SUCCESS) {
    currentRun.setStatus(JobRunStatus.SUCCESS);
    currentRun.setEndTime(event.getTimestamp());
}
jobRunRepository.save(currentRun);

Layer 1 (eventId): Checks "Have I already seen this exact message before?" (prevents duplicate processing).
Layer 2 (State check): Checks "Does it make business sense to update the database from the current status to the new status?" (prevents old or out-of-order messages from corrupting the state)

Together, they make your system 100% resilient to network lag, retries, and duplicate messages!

PostgreSQL does not update rows in place. Every UPDATE writes a new row version to disk and leaves dead tuples behind. 500 writes/sec just to update a timestamp column will:
1. Cause massive table bloat on job_runs.
2. Put heavy lock contention and write IOPS on the database.
3. Force PostgreSQL autovacuum to run aggressively, eating up CPU.

Hence to avoid this issue, while still keeping the executor-service heartbeat checking functionality we will use the Redis cache

How the Redis Heartbeat Approach Actually Works
This pattern is known in engineering as a "Dead Man's Switch" (like in trains, where the driver must press a pedal every 30 seconds; if the driver passes out and stops pressing, the train automatically detects it).

## Step-by-Step Breakdown

Step 1: Executor Sends Heartbeat (Every 10 seconds)

Inside executor-service, a tiny scheduled background method runs every 10 seconds:

java

// Spring Boot code inside executor-service:

@Scheduled(fixedRate = 10000) // every 10s
public void sendHeartbeat() {
    // Sets key with a 30-second auto-expiration (TTL)

    redisTemplate.opsForValue().set(
        "executor:" + myExecutorId + ":heartbeat", 
        "ALIVE", 
        Duration.ofSeconds(30)
    );
}
Cost: 1 network call in memory (~0.2 milliseconds).
Load on Postgres: 0%.

Step 2: While Healthy
        - Every 10 seconds, the executor refreshes the key.
        - The 30-second countdown resets back to 30.
        - As long as the executor is healthy, the key never dies.

Step 3: What Happens if the Executor Crashes?
        - The worker process dies (power cut, machine failure, killed by OS).
        - It stops sending heartbeats.
        - After 30 seconds, Redis automatically evicts the key from memory.

Step 4: Watcher Recovers the Abandoned Jobs
        - watcher-service periodically scans running jobs:

        It queries: SELECT * FROM job_runs WHERE status = 'RUNNING'
        For each running job, it checks: redisTemplate.hasKey("executor:" + run.getExecutorId() + ":heartbeat")

        If the key exists: 
                - the worker is alive, job is fine.

        If the key is gone:
                - The worker has died!
                - Watcher marks that run as status = 'EXECUTOR_DIED' in the database.
                - Watcher re-publishes the job to Kafka run topic so another healthy worker can pick it up.




Why this is so superior to the Kafka $\rightarrow$ Postgres approach:

1. Zero Database Churn: PostgreSQL is not burdened with hundreds of useless UPDATE queries every few seconds.
2. Instant & Automatic: You don't write complex cleanup logic for dead workers—Redis's TTL does the deletion for free.
3. High Scale: 10,000 executors sending heartbeats every 10 seconds to Redis consumes less than 2% of Redis's CPU capacity.



The Killer Feature for Heartbeats: Auto-Expiring Keys (TTL)

        - In PostgreSQL, if you write a row, it stays there forever until you explicitly run a DELETE query.
        
        - In Redis, you can attach a TTL (Time To Live) to any key:
          "Hey Redis, store this key executor:worker-1:heartbeat, and automatically delete it after 30 seconds."
        
        - This is what makes Redis the foundation of health checking in distributed systems.
